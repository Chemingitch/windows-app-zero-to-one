# 仿作模式 · 照着现有软件 / 安装包 / 截图 / 文字描述做一个

当用户说"做一个像 XX / 仿 XX"，**或上传了一个 exe / apk / 截图**，**或用文字描述想要的功能**时，进入**仿作模式**。

核心原则：**先模仿其"形"（界面、图标、入口、布局），功能（必做 / 可选 / 不做）由开发者自己想，或你帮它大致推测里面有什么，再让开发者拍板。** 仿作是"做出同等体验的最小实现"，不是逐像素复刻。

## 触发信号

- "做一个像 <软件名> 的" / "仿 <软件名>" / "照着 <软件名> 做一个"
- 用户**上传了一个 exe / apk**
- 用户**上传了一张截图**
- 用户**用文字描述功能**（"我要一个能 XX 的" / "帮我做个能 YY 和 ZZ 的工具"）
- "XX 挺好用，给我来一个"

只要用户拿某个**已存在的软件 / 安装包 / 截图 / 一段功能描述**当参照，就走这一节，不要直接进入选型。

## 五种参照物，怎么取"形"

| # | 参照物 | 怎么"模仿其形" | 功能从哪来 |
|---|---|---|---|
| 1 | 软件名（"像 XX"） | 让开发者描述，或你按常识给 UI 草图 | 开发者定 / 你推测 |
| 2 | 上传的 **apk** | 用工具链 `aapt2 dump badging` 取包名、入口 Activity、权限、特性、图标；看 res 布局与 strings | 从权限 / Activity / 字符串**推测**，开发者确认 |
| 3 | 上传的 **exe** | 看图标、`(Get-Item).VersionInfo` 版本信息、manifest；有截图就看界面布局 | 从界面与同类软件推测，开发者确认 |
| 4 | 上传的**截图** | 直接照布局 / 配色 / 控件复刻界面 | 开发者定 / 你推测 |
| 5 | **用户文字描述的功能** | 功能已由用户给出，形由你给 UI 草图或参照同类软件 | 功能已由用户描述，你来落地 |

> 形态 2/3/4 是"先有形"；形态 1/5 是"先有功能，你来补形"。两条路都行，最终都汇成「形 + 功能清单」。

## 必须一次性追问的功能点

用 AskUserQuestion 或一轮连续的提问，把功能拆成三档。不要挤牙膏式追问。

| # | 要问的 | 为什么 |
|---|---|---|
| 1 | 参照物是软件名 / exe / apk / 截图 / 文字描述？ | 决定上面怎么取"形" |
| 2 | 你最在意它的哪一点？ | 抓住"灵魂"，避免被表面 UI 带偏 |
| 3 | **必做**的核心功能（逐条列出来） | 圈定 MVP，第一版只做这些 |
| 4 | 可以**砍掉 / 简化**的功能 | 先做最小可用，后续再迭代 |
| 5 | 目标形态：窗口 / 命令行 / 常驻后台 | 复用 SKILL.md 阶段 0 的形态询问 |
| 6 | 有没有界面参考（截图 / 描述 / 配色） | 减少来回确认，直接对齐观感 |
| 7 | 数据从哪来？要不要**兼容原软件的文件格式**？ | 决定本地存储 vs 联网、是否要解析旧格式 |
| 8 | 给谁用、要不要联网 | 影响签名策略与杀软误报 |

## 产出格式

一份不超过 15 行的清单，分三档：

```
定位：做一个像 <软件> 的 <一句话>
形：界面草图（顶部栏 / 侧边栏 / 列表 / 按钮 / 配色）——从参照物取
必做：
  - 功能 A
  - 功能 B
可选（后续迭代）：
  - 功能 C
不做（第一版砍掉）：
  - 功能 D（原软件有，但本次不需要）
形态：窗口程序 / 命令行工具
数据：本地单文件 / 联网 API
```

拿到这份清单后，再进入 SKILL.md 阶段 1 选型（Go / .NET / Python）。

## 从安装包 / 截图 / 文字推测功能的线索

- **apk**：`aapt2 dump badging` 后看 `uses-permission`——`CAMERA`→拍照类、`INTERNET`→联网、`READ_CONTACTS`→通讯录、`ACCESS_FINE_LOCATION`→定位；入口 Activity 数量暗示有几个页面；`res/values/strings.xml` 里的词暴露功能点。
- **exe**：`(Get-Item app.exe).VersionInfo` 的 `ProductName / FileDescription / CompanyName` 常直接暴露用途；有界面截图就看布局；若用户允许，可用 `sigcheck -a` 看签名与公司信息辅助判断。
- **截图**：直接照布局复刻——顶部栏 / 侧边栏 / 列表 / 按钮 / 配色，先出静态骨架。
- **文字描述**：功能已由用户给出，重点是帮他把"描述"翻译成"必做 / 可选 / 不做"三档，并补上界面草图。

> 推测只是辅助，最终由开发者确认。不要替用户拍板功能范围。

## 示例 1：做一个像"记事本"的程序

追问后得到：

```
定位：轻量纯文本编辑器
形：单窗口 + 菜单栏（文件/编辑）+ 编辑区
必做：
  - 打开 / 编辑 / 保存 .txt
  - 新建窗口
  - 字号缩放
可选：
  - 查找替换
  - 自动换行开关
不做：
  - 语法高亮（VS Code 的事）
  - 云同步
形态：窗口程序（WinForms）
数据：本地文件
```

→ 选 C# + dotnet CLI（原生 GUI，不用 VS），直接 `dotnet new winforms`。

## 示例 2：上传一个 apk，仿它的本地搜索

用户丢来一个 `search.apk`：

```
aapt2 dump badging search.apk
  package: com.xx.search
  launchable-activity: .MainActivity
  uses-permission: INTERNET, READ_EXTERNAL_STORAGE
  uses-feature: touchscreen
```

推测：联网 + 读存储 → 多半是"搜本地文件 + 可能云"。但用户只想要"本地极速搜"，于是砍掉联网：

```
定位：极速本地文件名搜索
形：单框输入 + 结果列表（路径 + 双击打开）
必做：
  - 输入即过滤文件名
  - 结果显示路径 + 双击打开
可选：
  - 正则匹配 / 按修改时间排序
不做：
  - 全文内容索引（太重）
  - 网络搜索
形态：窗口程序（其实是照搬其 Android 形态到 Windows 桌面）
数据：只读本地文件系统（不写任何东西）
```

→ 选 C# 或 Go；强调"只读、不写盘"，降低杀软误报。

## 原则

- **仿作 ≠ 复刻**：做出同等体验的最小实现，先交付能用的，再迭代。
- **形先功能后**：先交"形"（界面骨架 + 图标 + 入口），功能（必做 / 可选 / 不做）由开发者自己想，或你帮它大致推测里面有什么，再让开发者拍板。
- **功能 > 界面**：先定必做功能，界面只是载体。
- **敢砍**：用户说"像 XX"时往往只想要 XX 的某一个点，帮他把其它点砍掉。
- **格式兼容要问**：很多仿作掉坑在"要不要读原软件的文件"，这一条一定要问。
- **推测要标注**：从安装包/截图推测的功能只是辅助，务必让开发者确认，别替他拍板。
